Architecture

The Guardian is one Python program with two front doors: a CLI (main.py --mode …) and a FastAPI web dashboard (main.py --mode serve). Both call the same Engine. A scan is a straight pipeline. Each stage hands the next a typed Pydantic object, so the dashboard receives exactly what the validator checked.

Four modes reuse the same pipeline

Full scanStages 1–6 on a repo. Records a baseline SBOM on first run.Engine.scanThe Day 1 checkpoint and the Day 2 prioritised list.
Pre-install gateChecks a package before install from registry metadata only: typosquat distance, non-existent name, release age < 7 days, install hooks with exec/network/secret sinks, MAL- reports, known CVEs. BLOCKED at score ≥ 80 or on a hard signal. CLI exit code 3.run_pre_cve_admission_check, Engine.check_pkgCatches attacks that have no CVE yet.

Where the AI sits, and where it cannot reach

The rule for Day 2 is that an LLM may explain and gather evidence, but never decide. That rule is enforced by code, not by the prompt. The diagram shows the only paths Gemini's output can take.

Tools

get_risk_breakdown, get_attack_tree_paths, read_code_lines (refuses .., .git/, .env, keys, .npmrc), inspect_manifest_or_diff, get_advisory_metadata. Every one is read-only.

Validator

finding exists · file exists inside the repo · snippet appears verbatim within ±5 lines · purl is in the SBOM · purl matches the finding · risk breakdown equals compute_risk(factors) · explanation doesn't claim a different level, score or priority · every attack-path edge is in the graph and starts at an entrypoint · fix command uses an allow-listed prefix · for vulnerabilities, the command acts on the package or its root-cause target.

Call-site check

Accepted only when reachability is still unknown and the package is a direct dependency, and all of these hold: the file is a non-test source that imports the package; the quoted line exists verbatim; the line calls binding.fn( or a named import fn(; fn is named in the advisory itself. The agent can only raise a score with proof. It can never lower one.

Why

An LLM's knowledge of CVEs is stale and it can be talked into things. Scores come from dated feeds and a formula you can recompute by hand, so a judge or a developer can audit every number. The LLM adds what it is good at: plain-language explanation and searching code for evidence.

The risk engine (Day 2 · objective 1)

risk_engine.compute_risk(factors) is a pure function: the same inputs always give the same breakdown. Known vulnerabilities score on five factors that add up to 100. Supply-chain attacks without a CVE start from a fixed threat-class base instead.

FactorMaxHow it maps to pointsIf unknownSource
CVSS severity35linear: 9.8 → 34.3, 7.5 → 26.25.0 prior, confidence −0.25OSV vector; NVD when OSV has none; label estimate as last resort
EPSS exploit probability25log scale: 0.001 → 2.5, 0.01 → 8.7, 0.1 → 16.7, 0.92 → 24.70.01 prior, confidence −0.10FIRST EPSS API, dated per CVE
CISA KEV20listed 20, not listed 00, confidence −0.10CISA KEV JSON feed, catalogue version recorded
Reachability10confirmed 10 · imported or unknown 5 · not imported 2 · vulnerable function never called 05, confidence −0.20import index + call search; known parent→child calls (express→qs.parse); verified agent call sites
Exposure10public unauthenticated route 10 · network service 6 · internal/CLI 25, confidence −0.10route mounts in server.ts/app.ts, listen(), Dockerfile EXPOSE; or SCG_EXPOSURE

Adjustments, each printed on the card: a MAL- advisory (malicious package) sets the score to 100. A KEV listing sets a floor of 80 (60 if the code is proven unused). Dev/test-only dependencies are multiplied by 0.6, except install-time attacks, which hit developer machines and CI anyway. Dependency depth is shown but never scored: a transitive package is not safer just because it is deeper. Bands: Critical ≥ 80 · High 60–79 · Medium 30–59 · Low < 30. Priority: P1 act now (Critical or KEV) · P2 fix soon · P3 plan · P4 monitor.

Confidence starts at 1.0. It drops for every assumption the score had to make: CVSS estimated from a label, no EPSS, KEV not checked, reachability unknown, version guessed from a range floor, exposure inferred from code rather than deployment, demo data. High ≥ 0.8, medium ≥ 0.5. The reasons are listed under the score.

What the weights imply. CVSS is capped at 35, so a CVE can only become Critical with exploit evidence: a KEV listing, or EPSS near 0.9 plus reachable and exposed. On the test repo, yesterday's Elo marked 16 findings Critical. The engine now marks one (a known-malicious package), plus 5 High, 124 Medium and 188 Low. That is the point of prioritisation. It's also a choice the team should agree on before the demo.

One finding, end to end

Here is what happens to qs@6.5.2 in the test repo (1,091 packages, lockfile committed). Nothing below is mocked.

Discover

The npm v3 lockfile parser finds node_modules/qs 6.5.2 under body-parser 1.18.3, express 4.16.4 and request 2.88.0. It records each parent's declared range, e.g. body-parser requires 6.5.2 exactly.

Detect

OSV returns GHSA-hrpp-h998-j3pp (alias CVE-2022-24999). fixed_version_for picks the fix for the affected range that contains 6.5.2, not just the first fix listed.

Enrich

EPSS 0.2004 (98th percentile, dated 2026-11-23). Not in CISA KEV catalogue 2026.11.23. CVSS 7.5 from the OSV vector.

Graph

Attack path: server.js --imports--> body-parser@1.18.3 --depends_on--> qs@6.5.2 --calls--> GHSA…. Each hop carries its evidence (file:line or lockfile entry).

Score

26.2 + 19.2 + 0 + 10 + 10 = 65, High, P2. Confidence 0.95 (the only deduction: exposure was inferred from routes, not deployment config).

Root cause

blocked-by-parent: body-parser 1.18.3 requires qs 6.5.2, express requires 6.5.2, request requires ~6.5.2. None of these ranges admits the fix, so a lockfile refresh can't help.

Fix

Group G-02: "Upgrade body-parser, cypress, express to a release whose tree allows qs 6.16.0+, or force it with an overrides entry." Command: npm pkg set overrides.qs=6.16.0 && npm install --ignore-scripts

Card

All 10 validator checks pass. In the dashboard: score bar, components, confidence reasons, five dated sources with links, root cause, copyable command, "show in dependency graph".

Day 1 in detail

1 · Discover components done (npm)

What

Every package with name, version, purl, integrity hashes, direct or transitive, dev or runtime, and where the version came from.

Where

scanners.run_cdxgen, parse_npm_lock, resolve_npm_edges, _sbom_from_lock, build_import_index

How

It tries sources in order of precision: cdxgen with --no-install-deps; the committed lockfile (npm v1/v2/v3, with Node-style resolution of nested node_modules); a lockfile resolved from registry metadata in a temp dir (npm install --package-lock-only --ignore-scripts, opt-in); and as a last resort the package.json range floor, flagged on every card.

Why

Many repos (Juice Shop, dvna) commit no lockfile, so the manifest alone shows about 20 direct deps when 300+ are really installed. Resolving metadata-only gives the real tree without running any package code.

2 · Build the supply chain view done

What

A CycloneDX SBOM, a dependency graph, and inspection of containers and CI.

Where

write_cyclonedx → .scg_cache/…/bom.cdx.json; dep_graph.DependencyIndex; inspect_dockerfile, inspect_workflow; the collapsible tree in the Dependencies view

How

NetworkX DiGraph from project to direct to transitive. BFS gives depth and one shortest path per package; descendant sets give introduced_by (which direct deps pull a package in). Packages with no recorded parent are attached as "inferred direct" so nothing disappears. Each edge carries evidence: a package.json line, or a lockfile entry with its declared range.

Why

Root-cause fixes need parents and ranges, and the explorer needs to stay usable at 1,000+ nodes. A collapsible tree with "only paths to critical & high" stays readable where a force layout becomes a hairball.

3 · Detect vulnerabilities done

What

CVE/GHSA/MAL ids, CVSS, fixed version, and a trace back to the direct dependency responsible.

Where

run_osv_scanner, _parse_osv_scanner_json, parse_osv_record, fixed_version_for, cvss3_base_score

How

First choice is osv-scanner scan source -L bom.cdx.json, the same inventory the graph shows. Next is the lockfile, then the OSV.dev batch API, then clearly labelled demo data. GHSA + CVE alias groups are counted once. CVSS v3 is computed from the vector in Python.

Why

Scanning the SBOM rather than the repo means the vulnerability list and the graph can never disagree about what is installed.

4 · Detect suspicious changes done

What

Typosquats, unexpected dependencies, suspicious updates, unsafe install scripts, untrusted images, modified lockfiles.

Where

run_static_supply_chain_inspector, compare_lock_hashes, inspect_manifest_hooks, nearest_popular (OSA distance), run_pre_cve_admission_check, Engine.replay

How

Lockfile integrity is compared against git show HEAD~1:package-lock.json and a baseline SBOM: a changed hash with no version bump is tampering. Install hooks are scanned for curl/wget, pipe to shell, eval, base64, env or secret-file reads. Dockerfiles are checked for :latest, missing digest, untrusted registry and curl | sh. Workflows are checked for actions not pinned to a 40-char SHA. Replay diffs manifests per commit and gates every new dependency.

Why

The worst supply-chain attacks (event-stream, ua-parser-js, the xz backdoor) had no CVE when they landed. These checks look at behaviour and provenance instead of advisory databases.

5 · Present evidence done

What

For each finding: what was detected, the affected component, the dependency path, supporting evidence, the risk level.

Where

models.EvidenceCard, orchestrator.draft_deterministic_card, PostCheckValidator, static/index.html, main.print_cards

How

Five fields: (1) finding with purl and ids, (2) location with a verbatim code snippet, (3) attack path with evidence per hop, (4) risk breakdown, (5) remediation. A card only shows "verified" when every validator check passes.

Why

"Explain with evidence" means a reviewer can open the file and line and see it for themselves. The validator guarantees that is possible.

Day 2 in detail

The final demonstration is a chain. Here is how far the Guardian gets along it today.

Prioritized riskdone→ Recommended fixpartial→ Human approvalmissing→ Build & testmissing→ Rescanmissing→ Verified remediationmissing

1 · Prioritize risks done

Brief

Combine severity with exploitability, reachability and exposure; consider production use; separate urgent from low priority; explainable score and confidence.

Built

All of it: risk_engine.py (above), threat_intel.py (EPSS, KEV, NVD, cached 24 h, every value dated), dev/test scope ×0.6, P1–P4, confidence with reasons, Gemini explanations checked for contradictions, agent call-site evidence, and drift alerts when a CVE joins KEV.

2 · Investigate suspicious changes partial

Brief

At least one non-CVE risk; compare versions, manifests, lockfiles; find suspicious scripts, provenance gaps, integrity changes; separate verified evidence from AI inference.

Built

The detectors from Day 1 pillar 4, scored by threat class (tamper 90, typosquat 85, suspicious hook 80 …). Replay compares manifests and lockfiles per commit. The gate reads registry metadata for hooks added since the previous version and missing npm provenance. Cards carry author: deterministic | llm, and sources label agent (verified).

Missing

A dedicated investigation view per anomaly that lays out facts and AI inference in two visibly separate columns, and a version-to-version diff of what a package actually ships. That would mean reading tarballs in a sandbox; today we deliberately read metadata only.

3 · Recommend safe remediation partial

Brief

Upgrade, replace or remove, pin, update base image, block, escalate; include expected risk reduction, compatibility impact and rollback.

Built

Upgrade direct (npm install --ignore-scripts --save-exact pkg@x), refresh lockfile (npm update --ignore-scripts), pin via override, remove when no fix exists, block (the gate), digest-pin for images, SHA-pin for actions. Fix groups show where one change clears several findings.

Missing

Expected risk reduction (re-run the engine with the fixed version and show 65 → 0). Compatibility impact (flag major bumps such as micromatch 3 → 4 and breaking-change notes). A rollback command. "Escalate for security review" for low-confidence or no-fix cases. Concrete replacement packages and base-image tags.

4 · Validate the proposed fix not started

Brief

Apply the fix in a branch or sandbox, build, run unit and integration tests, rescan, compare before and after SBOMs, detect newly introduced vulnerabilities or dependencies.

Design call

This conflicts with the Guardian's core safety rule: it never runs project code. Building and testing is running project code. The safe way to do both is a throwaway container: a copy of the repo, the fix applied, egress allowed only to the npm registry, no host mounts or secrets, CPU and time limits, and lifecycle scripts kept off where the build allows. Afterwards, regenerate the SBOM inside the container and feed both SBOMs to the existing pipeline to diff.

5 · Verify & report not started

Brief

Original finding and evidence, the approved action, build and test results, before/after risk status, remaining or accepted risk, final confidence and audit trail.

Have

The pieces: evidence cards, fix groups, JSON output, a live log of every tool call and validator decision.

Missing

An approval record (who approved which group, when), the sandbox results, a before/after comparison, accepted-risk entries, and one exportable report that ties them together.

Safety model

A tool that inspects untrusted repositories is itself an attack target. These rules hold everywhere in the code.

RiskControl
Running untrusted codeNever runs npm install, project scripts or docker build. Subprocesses use argument lists, shell=False, timeouts and NPM_CONFIG_IGNORE_SCRIPTS=true. cdxgen runs with --no-install-deps.
Malicious git config or remoteClones run with hooks, fsmonitor, LFS smudge, symlinks and submodules off, https only and no credentials. History is read with git show and never checked out.
Registry lookupsJSON metadata only, never tarballs. Package names are regex-validated before a URL is built.
LLM hallucination or injectionRead-only tools, untrusted output fenced, secrets redacted, scores computed in Python, 10-check validator, deterministic fallback.
Dashboard abuseBinds to 127.0.0.1 (anything else needs --allow-remote). Host allow-list against DNS rebinding, Origin check and JSON-only POSTs against CSRF, all data HTML-escaped.
Fix commandsAllow-listed prefixes only, scripts always disabled, no ; | ` $(, only two permitted && chains.

Known limits

  • npm only for the SBOM. The former project also parsed Maven, Go and Python. Those parsers were not merged, because the base's attack tree and reachability are JavaScript-specific. PyPI exists only in the pre-install gate.
  • Reachability is regex and import based, not a call graph. It handles direct imports, one re-export hop and a curated list of parent→child calls. Unknown is scored neutrally, never as safe.
  • Exposure is inferred from source. Set SCG_EXPOSURE when the deployment is known.
  • NVD is rate-limited to 5 lookups per scan without NVD_API_KEY, so some CVSS scores remain label estimates (with lower confidence).
  • Overrides pin a package everywhere and can force a major bump. The text offers upgrading the parent as the alternative.
  • The attack-path view renders as a flat line on very large repos, a layout issue inherited from the base. The dependency tree view is the usable one there.
  • Gemini has only been exercised through a scripted fake in tests until it runs from the project venv with a real key.

Glossary

SBOM
Software Bill of Materials: the list of every component in an app. We write CycloneDX JSON.
purl
Package URL, a universal package id such as pkg:npm/qs@6.5.2.
OSV
Google's Open Source Vulnerabilities database. It knows which versions are affected and which fix them.
GHSA / CVE / MAL
Advisory ids: GitHub, MITRE, and OSV's malicious-package reports.
CVSS
Technical severity from 0 to 10. It says how bad a bug is, not how likely it is to be used.
EPSS
FIRST's daily estimate of the probability a CVE is exploited in the next 30 days.
CISA KEV
The US government's list of vulnerabilities known to be exploited in the wild.
Reachability
Whether the app's own code can actually reach the vulnerable function.
Lockfile
package-lock.json: exact versions and integrity hashes of the whole tree.
Override
An npm feature that forces one version of a nested package across the tree.
ReAct
An agent loop of think → call a tool → read the result → repeat, then answer.
